# API Reference

The backend uses Supabase edge functions for game logic. All functions accept POST requests with JSON bodies and require authentication via JWT in the `Authorization: Bearer` header.

## Edge Functions

### game-create

Create a new game.

**Request:**
```json
{
  "name": "My Game",
  "size": 40,
  "alliance": "day",
  "inviteEmail": "opponent@example.com",
  "themeId": "uuid-or-null",
  "aiOpponent": false,
  "mapConfig": {
    "forestDensity": 0.5,
    "mountainDensity": 0.5,
    "waterLevel": 0.5
  }
}
```

| Field | Required | Default | Description |
|-------|----------|---------|-------------|
| `name` | no | auto-generated | Game name |
| `size` | no | 15 | Board size (NxN) |
| `alliance` | no | `"day"` | Creator plays as day or night |
| `inviteEmail` | no | null | Opponent's email |
| `themeId` | no | null | Visual theme UUID |
| `aiOpponent` | no | false | Enable server-side AI opponent |
| `mapConfig` | no | defaults | Terrain generation parameters |

**Response:**
```json
{
  "id": "game-uuid",
  "name": "My Game",
  "size": 40,
  "currentPlayer": "day",
  "createdAt": "2026-03-25T12:00:00Z"
}
```

When `aiOpponent` is true, the opponent's email is set to `"ai@bot"` and the game-action endpoint will automatically play AI turns.

Instead of `inviteEmail`, the request may carry `inviteUsername` — a friend's claimed username. The function resolves it to the account's email with the service role, so emails never pass through the client. Games store `day_player_name`/`night_player_name` (stamped at create and join) so lists can show usernames instead of emails.

Usernames and friendships live in the `profiles` and `friendships` tables, accessed directly from the client under RLS: usernames are readable by any signed-in player (no emails in the table), a friendship row is visible only to its two parties, requests are inserted by the requester and accepted by the addressee.

### game-state

Fetch current game state. Response is filtered by fog of war based on the authenticated user's player role.

**Request:**
```json
{
  "gameId": "game-uuid",
  "since": "2026-03-25T12:00:00.000Z"
}
```

`since` is optional: the `updatedAt` of the last state the client received. When the game has not changed since then, the response is just `{ "notModified": true, "updatedAt": "..." }` instead of the full board.

**Response:** Full game state including tiles, players, clock, `updatedAt`, and game-over status. Non-visible tiles are replaced with `unexplored` landscape.

After every state change the server also broadcasts an `updated` event (payload: `{ updatedAt }`, no game data) on the Supabase Realtime channel `game-{gameId}`. Clients subscribe to that channel and call `game-state` when poked, with a slow fallback poll in case a broadcast is missed.

### game-action

Submit a game action. Validates the user is authorized to play as the claimed player.

**Request:**
```json
{
  "gameId": "game-uuid",
  "action": {
    "type": "move",
    "player": "day",
    "from": { "row": 5, "column": 3 },
    "to": { "row": 5, "column": 4 }
  }
}
```

**Response:**
```json
{
  "result": {
    "success": true,
    "message": "Piece moved"
  },
  "game": { "...filtered game state..." }
}
```

The response is sent as soon as the action is persisted; event logging, the realtime `updated` broadcast, and (when the opponent is AI, `ai@bot`) the AI's phase all run in the background after it. Clients pick up the AI's moves via the realtime poke or the fallback poll of `game-state`.

### game-join

Join an existing game as the night player.

**Request:**
```json
{
  "gameId": "game-uuid"
}
```

## Authentication

Uses Supabase Auth with email/password. The CLI stores sessions in `~/.config/hofap/session.json`. The web frontend uses `@supabase/supabase-js` which manages tokens automatically.

## Database

Game state is stored as JSONB in PostgreSQL. The `games` table holds tiles, player resources, clock, and game-over state as JSON columns. Row-level security ensures players can only see games they're involved in.

## Shared Code

Edge functions import game logic from `@shared/` which maps to `supabase/functions/shared/`. This directory is generated by `pnpm copy:shared` (copies `src/shared/` before deployment). It is not checked into git.

### game-debug (development only)

Open, read-only inspection endpoint — **no authentication by default**. Set the `DEBUG_API_KEY` function secret to require it (`x-debug-key` header or `key` query param; `pnpm debug:game` reads it from `.env`) before the game has real players. All emails are stripped; each seat is reported as `human`, `ai` or `open`. Every response carries `engineVersion`, the git SHA the function was deployed from (stamped by `pnpm copy:shared`).

Accepts `GET` query parameters or a `POST` JSON body with the same keys.

| Query | Description |
|-------|-------------|
| `?action=list&limit=10` | Most recently updated games with a per-player piece summary |
| `?action=get&gameId=<id>` | Raw stored state (both players, no fog of war) |
| `?action=get&gameId=<id>&as=day` | State after fog-of-war filtering — exactly what the day client receives |

`get` responses have the shape `{ engineVersion, as, summary, game }`; `summary.pieces.day` / `.night` list every piece with row, column, kind, hearts, landscape and building, and `summary.visibleTiles` counts tiles not hidden by fog.

From the terminal: `pnpm debug:game list` or `pnpm debug:game get <id> --as night --summary`.

Anyone can read any game's full state through this endpoint while no key is set. Spectators of a game (via `game-state`) only ever see the union of both players' vision.
